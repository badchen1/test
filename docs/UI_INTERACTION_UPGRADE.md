## 1. 采纳清单

| # | 模式 | 落点 | 为什么适合这个应用 |
|---|---|---|---|
| 1 | 圆形主题切换 | 设置页「外观」 | 原本只能跟随系统，加手动切换后需要一次「有物理感」的转场，否则全屏换色会闪。 |
| 2 | 拖拽排序 | 主界面队列 | 解密是**串行**的，队列顺序就是优先级。「把这个先解开」是真实高频诉求。 |

| 5 | 文本展开 | 任务卡片错误详情、设置页说明 | 解密报错信息经常很长，之前会把整张卡片撑开，一个失败项能顶掉半屏。 |

| 9 | 卡片堆叠滚动 | — | **跳过** |
| 10 | 标签展开筛选 | 主界面筛选行 | 队列混了四个平台的文件时，用户常想「先只处理 QQ 音乐这批」，但又不想删掉其他的。 |

## 2. 逐项实现要点

### 2.1 圆形主题切换

`ui/RadialThemeVeil.kt` + `ui/Theme.kt` + `MainActivity.KugoRoot`

- 原理：切换瞬间底层 UI 已换成新配色；遮盖层用**旧主题的背景色**，以点击点为圆心
  从「半径 = 对角线」收缩到 0。视觉上是新主题从手指位置扩散开。
- **为什么不用旧界面截图**：截图要 `PixelCopy` / `GraphicsLayer.toImageBitmap`，
  每帧成本高且 API 24 上不稳定；本应用视觉主体就是背景 + 卡片面，
  一个「背景→面色」的竖向渐变已经足够像，且任意低端机上满帧。
- 圆心取自选项自身的 `positionInRoot()` 中心。用 root 坐标而不是本地坐标，
  因为遮盖层挂在根 `Box` 上，两套坐标系必须对齐。
- 顺序有个坑：必须 `veil.snapTo(1f)` **在**设置 `revealOrigin` 之前，
  否则会闪出一帧没有遮盖层的新主题（同一帧内两个状态一起生效才对）。
- 顺带修了一个真实缺陷：状态栏 / 导航栏图标明暗之前恒为浅色，
  现在随应用主题走（`WindowCompat.getInsetsController`）。

### 2.2 拖拽排序

`ui/MainScreen.kt` + `TaskCard` 的拖拽手柄

- **手势分区**：长按给多选、手柄给排序。两者都需要「按住」，共用长按会让用户无法预期；
  而「只有手柄能拖」是通行的心智模型。
- **拖动期间列表不变动**，松手时用 `拖动位移 / 行高` 算出跨越了几格，一次性提交 `moveTask(from, to)`。
  这比「边拖边实时重排」简单得多，也不会出现重排后手指与卡片脱节的问题。
- **有筛选时禁用拖动**：筛选后列表是子集，「第 3 项」在完整队列里未必是第 3 项，
  允许拖动会导致排序结果与预期不符。运行中也禁用。

### 2.3 批量勾选

`MainScreen.SelectionTopBar` + `TaskCard.SelectionIndicator`

- 长按任一卡片进入多选，顶栏整体替换成选择工具栏（已选 N 项 / 全选 / 删除），FAB 收起。
- **错峰体现在两处**：每张卡片的指示器进场延时 `index * 32ms`；
  指示器的**占位宽度**和进场比例联动，所以卡片内容是被推着让位的，
  而不是先留空位再淡入——后者看起来像凭空出现。
- 队列增删后会把已不存在的 id 从选中集合摘掉，否则「已选 N 项」会数出幽灵条目。

### 2.4 文本展开

`ui/ExpandableText.kt`，复用于任务错误详情、设置页所有说明块、Cookie 预览

- `animateContentSize` 驱动高度连续过渡，箭头 0→180° 旋转给状态变化一个锚点。
- **文案不够长时不渲染展开按钮**（阈值默认 44 字符）。这是这类组件最常见的缺陷：
  出现一个「点了没反应」的死按钮。
- 一个副作用：设置页从「一屏塞 1.5 个分组」变成「一屏能看 3 个分组」。

### 2.5 步骤条回弹

`TaskCard.SpringStepper`

- 三段：读取 / 解密 / 输出。填充量用 `spring(dampingRatio = 0.42, stiffness = 380)` 驱动，
  活动段会**略微越过目标再回落**——这个过冲就是「回弹」的全部来源。
- 阻尼比取 0.42：再低会晃得让人分心，再高就没有手感了。
- **只在「进行中」和「已成功」时出现**。失败时停在哪一步我们无从得知，
  与其画一条满格的假进度，不如把空间让给错误详情。

### 2.6 开关联动反馈

`SettingsScreen.RelatedSwitchRow` + `ui/Effects.kt`

- 依赖：父开关关闭时子开关置灰、失效、自动关掉，杜绝「设了但不起作用」的幽灵配置。
- 涟漪：父开关一变，子行外侧扩散一圈描边（`rememberRipplePulse`：1 → 0 衰减，同时 0.96 → 1.0 缩放），
  把「是你的变化影响到我」这条因果关系直接画出来。
- 「输出到自定义目录」开关**先选目录再置位**：用户在 SAF 里点取消时开关保持关闭，
  不让开关撒谎。

### 2.7 卡片曲线删除

`TaskCard` 横向拖动 + `graphicsLayer`

- 判定：位移超过卡宽 30% **或**释放速度超过 1000 px/s。
  只看位移会惩罚「快速小幅甩动」的用户，只看速度会误伤慢速长滑。
- 飞出轨迹：`translationX` 线性推进，`translationY = 130 * p²` —— 这是个真抛物线，
  越往外飞下沉越快，形成「被甩出去」的弧线；同时缩到 0.85、转 5°、淡出。
- 卡片背后按滑动比例露出红色删除底衬，越滑越显。
- 运行中的任务禁止左滑（正在跑的任务不能凭空消失）。
- 松手未达阈值时用 `spring(dampingRatio = 0.5)` 弹回原位。

### 2.8 标签展开筛选

`ui/FormatFilter.kt`

- 只渲染队列里**确实存在**的平台，不出现空标签。
- 选中时标签横向展开，尾部滑出该类目数量——数量是「选它值不值」的决策依据。
- 数量徽标用 `expandHorizontally` + `fadeIn`，收起时不占宽度，这才是「展开」而不是「显示」。
- 筛选中的平台被删完后自动回到「全部」，不会停在一个空列表上。
- 平台由扩展名推断（`platformOf`）：四家的扩展名互不重叠，直接映射比跨语言问一次 Go 层便宜。

## 3. 为什么跳过两条

### 3.1 滑杆惯性吸附（Velocity-Based Slide）

这个应用里**没有天然适合滑杆的连续参数**：

- 解密并发数？刻意做成串行的（CPU 密集，并发只会互相抢资源让进度回调打架）；
- 输出质量 / 压缩率？解密是无损还原，不存在可调档位；
- 进度拖动定位？解密过程不可断点续传，拖了也没有意义。

硬塞一个滑杆只会是装饰。这个模式更适合播放器进度、图片编辑强度这类场景，
将来如果加了「批量输出码率转换」，它会是首选。

### 3.2 卡片堆叠滚动（Stacked Card Scroll）

堆叠滚动的前提是「卡片之间有层级关系、且用户是在**翻阅**而非**检索**」。
本应用的两个列表都不满足：

- 主界面队列：核心需求是「扫一眼还有几个没处理完」，堆叠会遮挡信息、拉低扫描效率，
  而且与已经实现的拖拽排序在视觉语言上直接冲突（堆叠 = 有层级，排序 = 平级）；
- 设置页分组：全部内容需要同时可见以便对照，堆叠只会增加一次展开操作。

这个模式适合引导页、卡片式内容流、相册浏览这类场景。

## 4. 已知取舍与限制

| 项 | 说明 |
|---|---|
| 筛选状态下不能拖动排序 | 有意为之，见 §2.2。筛选与排序共用同一条标签行，UI 上已用提示文案说明。 |
| 拖动排序是「松手才落位」 | 不是实时重排。牺牲了一点跟手感，换来实现稳定（不会出现手指与卡片脱节）。 |
| 步骤条不显示失败停在哪一步 | `TaskItem` 没有记录失败阶段，需要改 Go 层错误码映射。属于后续可做项。 |
| 主题切换遮盖层不是真实截图 | 用旧主题的「背景→面色」渐变近似，代价是切换时看不到旧界面上的文字。低端机上这个取舍是划算的。 |
| 编译告警 4 条 | 都是 `Icons.Filled.ArrowBack/Login` 与 `Divider` 的弃用提示（应先代码就存在），不影响功能。 |

## 6. 构建（本机必须遵守的顺序）

交互层每次改动后重编，都要让 Gradle 面对一个**全新的输出目录**，
否则它要删自己上一轮的产物时会撞到写保护（`mapDebugSourceSetPaths AccessDenied`）。

```bash
source <工具链>/env.sh
cd <仓库>/mobile
# 输出目录每轮换新名字（build-r4 → build-r5 → …），不要删旧的，原因见 BUILD-NOTES §5
"<工具链>/gradle-8.11.1/bin/gradle" \
  --init-script mirrors.init.gradle \
  --init-script build-r4.init.gradle \
  --project-cache-dir="$PWD/.gradle-r4" \
  assembleDebug --console=plain --no-daemon
# 产物：mobile/build-r4/app/outputs/apk/debug/app-debug.apk
```

> 两个坑：
> 1. **不要写 `rm -rf build-out && gradle ...`** —— 批量删除会被安全钩子拦下，
>    `&&` 链断在第一步，gradle 根本没执行。
> 2. **日志名每轮也要换**（`build-r5.log` → `build-r6.log`）。目标已存在时 shell 重定向失败，
>    而随后的 `tail` 会读到**上一轮的旧日志**，里面可能赫然写着 `BUILD SUCCESSFUL`。
>    判断构建是否真跑过，要看产物目录的时间戳。
